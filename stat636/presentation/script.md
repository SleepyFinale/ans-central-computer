# STAT 636 presentation script

About 15 minutes, 10 slides. The same text is in each slide's speaker notes.
Planned total: about 14.5 minutes, leaving time for questions.


## 1. Aligning two robots’ maps with graph matching

Hi, I'm Santhosh. Our project is about a practical problem from our lab's robot fleet: two robots map the same building separately, and before they can share the work their maps have to be aligned. We treat that as a network problem: each map becomes a graph of its free space, and aligning the maps becomes matching the two graphs. The question is when that graph structure actually helps, compared with the image-based method the fleet uses now, and what limits it. (about 30 seconds)

## 2. Two robots, two maps, two coordinate frames

Our lab runs TurtleBot3 robots with 2D LiDAR. Each one builds an occupancy-grid map with SLAM, but each in its own coordinate frame: as you can see, Clyde's map of the same hallways comes out rotated relative to Inky's. To coordinate, the central computer has to find the rigid motion, a rotation and a shift, that lines them up; on the right, Clyde's walls in teal sit on Inky's after a 270-degree rotation. The fleet does this today with AKAZE, which matches image features on the two grids. It is careful but slow: it often answers only once the maps overlap a lot. So our question is: if we turn each map into a graph and match the graphs, do we get the alignment sooner, and is it ever wrong? Both matter, because a wrong alignment sends robots to the wrong places. (about 1.5 minutes)

## 3. Data: develop on one set, test on another

All the data is our own. For development we used five runs of a single robot in a three-room area and paired them with each other: 260 map pairs, using early snapshots and crops to get partial overlap. Every setting of the method was chosen on those. Then we ran nine two-robot runs with Inky and Clyde together, four in the rooms and five in a larger corridor area, and scored them only after the settings were frozen. Every 15 seconds we take the maps the robots had at that moment and ask each method for the alignment: 478 time points in total. The truth is a reference alignment from an exhaustive search over rotations and shifts of the final maps. We checked it by eye, and where the live merger merged, it agrees to about 10 cm. An answer counts as right within 30 cm and grossly wrong beyond 2 m. (about 1.5 minutes)

## 4. From a map to a graph to a matrix

Here is the network part. We thin the free space of a map down to its skeleton, the line equally far from the walls, and put a node every 25 cm, at junctions and at dead ends. Each node also gets its clearance, its distance to the nearest wall. That gives a graph like the one on the left. Its adjacency matrix, in the middle, is almost empty: these graphs are sparse, nearly trees, with a mean degree around two. So instead we use travel distances, the shortest-path length between every pair of nodes, and turn them into a Gaussian kernel, on the right, which is dense. The reason this works comes from the latent space models in class: you can read the nodes' real positions as latent positions, and the kernel is roughly a function of the distance between them. Distances do not change when you rotate a map, so K is the same matrix in both robots' frames. The unknown rotation simply drops out. (about 1.5 minutes)

## 5. Match, fit, then decide whether to trust it

Once each map is a graph, the question becomes: which node in Clyde's graph is the same place as which node in Inky's? That is graph matching. The formula at the top just says: pair up the nodes so that distances between nodes, and how far each node is from a wall, agree as well as possible in both graphs. Checking every possible pairing would take far too long, so we use a standard approximation called FAQ that finds a good pairing quickly. The whole method is these five steps. One, turn each map into a graph. Two, match the nodes. Three, use the matched nodes to work out how to rotate and shift Clyde's map onto Inky's; some matches will be wrong, so this step ignores the ones that don't fit. Four, a sanity check: if the aligned maps contradict each other, say a wall landing on open floor, we reject the answer. Five, we only trust an answer once we get the same one twice in a row, the same rule the fleet already uses. To make it a fair test, AKAZE goes through the same last step, and we also run a version that uses only each node's distance to the wall, with no graph connections, to see whether the graph structure itself is helping. (about 1.5 minutes)

## 6. Matching needs a matrix with no symmetries

So when should matching work, and when can't it? Think of both robots' graphs as two imperfect copies of the same building. The key idea is symmetry. If a graph looks exactly the same after you swap some of its nodes around, the matching has no way to tell the right pairing from the swapped one: both score equally well. The formula on the left is the math behind that. So matching only works when the graph has no symmetries like that. That explains what we saw. Using only which nodes are connected doesn't work: these graphs are mostly long chains, and a chain looks the same read in either direction. Even on an exact copy of a graph, that version matched only 13 to 17 percent of nodes. Using the distances between nodes does work: the distances pin down the whole shape, so it matched 100 percent. But corridors are risky: a loop of hallways can look almost the same rotated by 90 degrees, which is nearly a symmetry. The other limit is that the two robots don't build quite the same graph from the same place: only 62 percent of nodes show up in both. In simulation, losing that many nodes drops matching from 100 percent to 8. (about 2 minutes)

## 7. Graph matching was right first in 7 of 9 runs

First result: speed. Each bar is one test run: when the graph method first held a correct alignment, minus when AKAZE did. Negative means the graph method was first. It was first in 7 of 9 runs, by a median of 60 seconds, in the rooms and in the corridors. In two runs AKAZE was first, by 15 and 30 seconds. One bar is coral: in hall2 the graph method was technically first, but only after holding a wrong alignment for about nine minutes. I'll come back to that. Statistically: the runs are the unit, not the 478 time points, because consecutive time points see almost the same maps. A sign test on 7 of 9 gives a one-sided p of about 0.09: a consistent advantage, but nine runs are not enough to call it significant. (about 1.5 minutes)

## 8. Only the graph methods were ever wrong

Second result: correctness. Across all nine runs, this counts the time points at which each method was holding a right alignment, in teal, or a wrong one, in coral. FAQ held a right alignment slightly more often than AKAZE, 310 against 297, because it answers sooner. But AKAZE was never wrong in any run, and the graph methods were. Clearance alone and the two partial-matching variants were worse than FAQ, so the graph structure does add something over a node feature, though on the development data only about 5 to 9 percentage points. Two things on the right. In the three-room area, no method was ever wrong. And AKAZE's zero out of nine is not proof of a zero rate: with nine runs the exact upper bound is about 28 percent of runs. All of FAQ's grossly wrong time points come from one hallway run, hall2. (about 1.5 minutes)

## 9. In corridors the wrong answer repeats itself

So what happened in hall2? On the left is Clyde's map at 120 seconds, placed by the graph method in coral, and on the right the correct placement in teal. Clyde had mapped one corridor with a side opening. The graph method laid it along Inky's corridor turned 90 degrees, where it fits almost as well, while the truth is that Clyde's corridor continues Inky's. At that point the maps overlapped only about 7 percent. That is the near-symmetry from slide 6. Why did the confirmation rule not catch it? The rule only uses an answer after two in a row agree. If wrong answers are independent and scattered, committing to one needs two of them to agree, probability about q squared times pi, which is tiny. That works: without the rule FAQ accepted wrong answers in 7 of 9 runs, with it in 3. But here successive answers come from nearly the same maps, so the same wrong placement wins every time: pi is close to one, and the rule offers no protection. Once committed, it is held until three answers agree on something else, so it lasted about nine minutes. (about 1.5 minutes)

## 10. What we learned, and what remains open

To answer our question: graph structure helps where the space is distinctive. The graph method was first in 7 of 9 runs and never wrong in the rooms. It misleads where the space repeats: corridor symmetries produce consistent wrong matches that confirming over time cannot filter out. And on the network side, the useful structure was travel distance between nodes, not adjacency, and the real limit is how repeatably we build the graph from a map. What remains open, and how we would address it: first, the corridor ambiguity. The natural fix is to let the graph method propose an alignment early and use it only once AKAZE or another independent check agrees, combining the speed of one with the safety of the other. Second, graph construction: nodes that repeat across runs, for example junctions only. Third, statistical power: nine runs give a p of 0.09 and a 28 percent bound, so more runs and more buildings. And fourth, a measured ground truth, from surveyed start poses, instead of one estimated from the maps. Thank you, happy to take questions. (about 1.5 minutes)
